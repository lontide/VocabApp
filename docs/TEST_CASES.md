# 학습 목록 변경 테스트 케이스

상태: 신규 기능 구현 후 study.test.mjs와 browser.mjs로 핵심 경로를 검증했다. 아래 케이스는 전체 수용 기준이며 각 항목의 모든 환경 검증까지 완료한 것은 아니다. [SPEC.md](../SPEC.md)의 다음 변경 명세와 [TASKS.md](../TASKS.md)의 T-10~T-14를 기준으로 한다.

## 실행과 판정

- 기존 자동 회귀 검증: npm run check. 데이터·셔플·현재 4개 방향 매핑·기본 저장소 동작은 실제 assertion으로 검사한다. 매핑 검사는 현재 생성기를 임시 어댑터로 쓰며 공통 매퍼 구현 시 연결을 교체한다.
- tests/study-acceptance.test.mjs는 아래 케이스를 Node test.todo로 등록한다. TODO는 미구현/미검증이며 성공으로 집계하지 않는다. 구현 시 해당 TODO를 실제 앱 로직/컴포넌트 assertion으로 교체한다.
- unit은 로직 자동 검증, browser는 실제 DOM·모바일 조작 검증이 필요하다는 뜻이다. 가짜 구현을 테스트 안에 작성하거나 소스 문자열 포함 여부로 UI 성공을 판정하지 않는다.
- 공통 준비: 격리된 저장소, 실제 데이터의 서로 다른 A/B/C 표현과 최소 두 탄, 4개 학습 모드를 사용한다. 원본 순서 검증에는 ID 순서와 배열 순서가 다른 작은 fixture도 사용한다.
- 브라우저 결과는 환경·대상 커밋·TC ID·실제 결과를 기록한다. 단위 검증 통과로 브라우저 케이스 전체를 완료 처리하지 않는다.

## 케이스

### TC-01 — 어휘 리스트 진입·객관식 제거

- 연결: T-10 / 검증: browser / 상태: 대기
- 준비·절차: 1탄 선택 후 기존 퀴즈 위치의 어휘 리스트 버튼을 탭하고 카드로 복귀한다. 1·3탄 복수 선택으로 반복한다.
- 기대 결과: 객관식 진입이 없고 선택 범위 전체와 탄 소속을 표시한다. 카드 진행·모드·북마크를 보존한다.

### TC-02 — 4개 모드 질문·답안 매핑

- 연결: T-10 / 검증: unit + browser / 상태: 대기
- 준비·절차: 각 모드에서 같은 어휘의 목록 행과 카드를 확인한다.
- 기대 결과: 단어→뜻(word/meaning), 뜻→단어(meaning/word), 예문→뜻(ex_en/meaning), 한국어→영어예문(ex_ko/ex_en)이 일치한다.

### TC-03 — 초기 가림과 개별 공개

- 연결: T-10 / 검증: browser / 상태: 대기
- 준비·절차: 평가된 A와 미평가 B가 있는 목록을 열고 A의 답안 영역을 탭한다.
- 기대 결과: 평가와 무관하게 처음에는 모두 가린다. A만 공개되고 B와 평가 기록은 변하지 않는다. 보조 텍스트에도 답이 미리 나타나지 않는다.

### TC-04 — 가림 초기화

- 연결: T-10 / 검증: browser / 상태: 대기
- 준비·절차: 한 행을 공개한 뒤 모드 변경, 탄 변경, 순서 변경, 카드 왕복, 새로고침을 각각 수행한다.
- 기대 결과: 각 목록 재진입/설정 변경 후 답안을 다시 가린다. 기록과 북마크는 유지한다.

### TC-05 — 미평가·평가 전환과 반복

- 연결: T-11 / 검증: unit + browser / 상태: 대기
- 준비·절차: 미평가 A에서 외웠어요→외웠어요→헷갈려요→외웠어요 순서로 탭한다.
- 기대 결과: 초기 두 버튼 미선택, 이후 항상 최신 버튼 하나만 선택된다. 같은 버튼 반복은 해제나 중복 집계를 유발하지 않는다.

### TC-06 — 어휘·모드별 독립성

- 연결: T-11 / 검증: unit / 상태: 대기
- 준비·절차: A/단어→뜻을 외웠어요, A/뜻→단어를 헷갈려요로 기록하고 B와 나머지 모드를 조회한다.
- 기대 결과: 두 기록은 독립적이고 B 및 나머지 모드는 미평가다. 한 기록을 변경해도 다른 조합은 유지된다.

### TC-07 — 카드·목록 기록 공유와 진행 보존

- 연결: T-11 / 검증: browser / 상태: 대기
- 준비·절차: 두 번째 카드에서 평가한 뒤 목록으로 이동하고 같은 항목을 반대로 평가한다. 다른 행도 평가한 뒤 카드로 돌아간다.
- 기대 결과: 최신 평가가 두 화면에서 일치한다. 목록 편집은 카드 진행을 넘기지 않고 자동 스크롤하지 않는다.

### TC-08 — 영구 기록 및 재시도 보존

- 연결: T-11 / 검증: unit + browser / 상태: 대기
- 준비·절차: 평가·북마크 후 새로고침, 재방문, 모드·탄 전환, 순서 전환, 전체/헷갈리는 항목 재시도를 수행한다.
- 기대 결과: 같은 브라우저/사이트에서 모드별 기록과 북마크는 유지한다. 공개 상태·카드 위치·섞인 배열은 영구 복원하지 않는다.

### TC-09 — 손상된 저장소·접근 거부

- 연결: T-11 / 검증: unit / 상태: 대기
- 준비·절차: 깨진 JSON, null, 객체, 잘못된 ID/모드/상태, 미지원 스키마 버전, getItem/setItem 예외를 각각 주입한다.
- 기대 결과: 앱이 중단되지 않고 안전하게 기본값/정제 값으로 복구한다. 정상 북마크·설정을 삭제하지 않고 UI 평가는 가능하다.

### TC-10 — 구버전 quiz 설정 전환

- 연결: T-10 / 검증: unit + browser / 상태: 대기
- 준비·절차: 기존 study_style=quiz, 선택 탄·모드·북마크를 저장한 상태로 앱을 시작한다.
- 기대 결과: 카드로 안전하게 진입한다. 기존 탄·모드·북마크는 유지하고 과거 세션 점수로 새 기록을 만들지 않는다.

### TC-11 — 기본 원본 순서와 정확한 복원

- 연결: T-12 / 검증: unit / 상태: 대기
- 준비·절차: 순서 설정 없는 상태로 시작한다. ID가 행 순서와 다른 데이터 및 역순으로 선택한 복수 탄으로 섞기→원본을 수행한다.
- 기대 결과: 기본은 원본이다. 결과는 원본 items 배열을 선택 탄으로 필터링한 순서와 같고 ID/알파벳/클릭 순서로 정렬하지 않는다.

### TC-12 — 섞기 항목 보존과 입력 불변

- 연결: T-12 / 검증: unit / 상태: 대기
- 준비·절차: 빈 배열·한 항목·복수 탄 배열에 섞기를 적용한다. 난수는 제어 가능한 방식으로 주입/고정한다.
- 기대 결과: 항목 집합·개수·탄 소속이 보존되고 입력 배열은 변경되지 않는다. 우연히 같은 순서가 나왔다고 실패하지 않는다.

### TC-13 — 섞기 안정성과 공유

- 연결: T-12 / 검증: unit + browser / 상태: 대기
- 준비·절차: 섞기 후 답안 공개·평가·재렌더·카드/목록 전환을 반복한다.
- 기대 결과: 처음 생성한 순서를 유지하며 카드와 목록이 동일 순서를 사용한다. 범위/순서 변경 때만 새 순서를 만들고 기록은 보존한다.

### TC-14 — 순서 설정 저장·복구

- 연결: T-12 / 검증: unit + browser / 상태: 대기
- 준비·절차: 섞기를 선택하고 재방문한다. 이어 잘못된 순서 값과 저장소 거부로 시작한다.
- 기대 결과: 선택 설정만 저장한다. 섞기 재방문은 새 배열을 생성하고 잘못된 값/접근 거부는 원본으로 복구한다. 카드 위치는 처음부터 시작한다.

### TC-15 — 범위별 집계와 헷갈리는 항목 재학습

- 연결: T-11 / 검증: unit + browser / 상태: 대기
- 준비·절차: A 외웠어요/B 헷갈려요/C 미평가를 만들고 A 반복 평가·이전 이동·반대 평가·모드 전환을 수행한다.
- 기대 결과: 현재 범위/모드의 최신 기록만 집계한다. 미평가는 외웠어요로 세지 않고 정답률은 0~100%다. 재학습은 해당 모드의 헷갈려요만 포함하며 기록을 지우지 않는다.

### TC-16 — 모바일 터치·긴 텍스트·전체 탐색

- 연결: T-13 / 검증: browser / 상태: 대기
- 준비·절차: 좁은 모바일 화면에서 긴 예문 모드와 복수 탄 목록을 열고 마지막 항목까지 탐색한다. 키보드 없이 공개·평가·순서 선택·카드 복귀를 수행한다.
- 기대 결과: 가로 넘침·버튼 겹침 없이 모두 조작할 수 있다. 평가 탭이 답안 공개를 유발하지 않는다. 학습 UI에 단축키 안내가 없다.

### TC-17 — 선택 상태와 공개 조작 접근성

- 연결: T-13 / 검증: browser / 상태: 대기
- 준비·절차: 평가 버튼과 가림 영역을 보조기술/키보드로 탐색하고 상태를 변경한다.
- 기대 결과: 색상 외 표시와 선택 상태, 답안 공개 여부·조작 목적이 전달된다. 가려진 답이 보조기술로 미리 읽히지 않고 모바일 터치도 동일 동작이다.

## 기존 검증과의 관계

객관식 보기 개수·정답 보기·오답 중복 허용 테스트는 폐기한다. 4개 방향 질문/답안/TTS 매핑, 데이터 무결성, 셔플의 입력 불변 검증은 유지한다. 기존 저장소 검사는 신규 기록·스키마 복구·quiz 전환을 검증하지 않으므로 TC-09/TC-10 구현까지 완료로 표시하지 않는다. T-14 전체 완료는 실제 신규 assertion과 브라우저 결과가 모두 확보된 후 판단한다.

## UI 편의 개선 케이스

- UI-01: 320/390/1280px에서 가로 넘침과 설치 안내의 fixed 겹침이 없어야 한다.
- UI-02: 마지막 행까지 스크롤해도 목록 도구가 화면 상단에 남고 맨 위로 버튼으로 돌아간다.
- UI-03: 검색 질문/답안·대소문자·공백·모드별 상태·AND 필터·빈 결과·초기화를 검증한다.
- UI-04: 미평가 필터에서 평가해도 행 개수가 유지되고 명시적 새로고침 후에만 줄어든다.
- UI-05: 답안 공개 후 재가림 시 답은 숨고 평가·카드 진행은 변하지 않는다.

자동 검증: tests/list-filter.test.mjs, 브라우저 검증: node tests/ui-browser.mjs. 구현 전에는 실패하는 테스트다.

UI-01~UI-05 구현 후 list-filter.test.mjs와 ui-browser.mjs(320/390/1280px), 기존 browser.mjs가 로컬에서 통과했다. 실제 휴대폰 검증을 의미하지 않는다.
